三、后端接口一览（cs/Controllers，路由 = api/[controller]，[HttpPost("xxx")]）
================================================================================

  #1  注册                       POST /api/Auth/register
      前端发（UserDto, json camelCase）
        { "name": "xxx", "gender": "boy|girl", "call": "olderBrother|shota|
          olderSister|loli", "apiKey": "sk-xxx" }
      后端回
        成功: { "code": 200, "message": "注册通过了喵", "data": { "id": 12, "token": "eyJ..." } }
        重名: { "code": 400, "message": "用户已存在", "data": {} }   ← 注意这里 data 是空对象
      说明
        data.id 是 User.Id（数字）；token 是 JWT，claims 里放了 UserId 和 Name
        apiKey 是用户自己的 DeepSeek Key，注册时一并入库，后续所有 AI 调用都用它

  #2  聊天                       POST /api/Chat/chat1
      前端发（UserChatDto）
        { "userName": "xxx", "sessionId": 12|null, "type": "text", "message": "你好" }
        sessionId 为 null = 新会话（后端建 Session 并把用户塞进 SessionParticipant）
        前端自己从 localStorage["sessionId_<aiName>"] 读 sessionId
      后端回
        { "code": 200, "message": "Ok",
          "data": { "sessionId": 12, "message": "AI的回复文本" } }
        找不到用户: { "code": 400, "message": "根本没有这种userId!" }
      后端处理流程
        查 userId → 查 apiKey → 无 sessionId 则 CreateSessionAsync
        → 存用户消息 SaveChatInMessageAsync → GetChatHistoryAsync 整段历史
        → MapRoleContent 转 RoleContent 格式 → SendToAi → 存 AI 消息
        → AddAIInDbAsync(reply.aiName) + AddUserInSessionParticipantAsync
        映射规则：Messages.UserId == 当前 userId ? "user" : "assistant"

  #3  预人设（打招呼 + 自选人设）  POST /api/PrePerson/preperson1
      前端发（PrePersonDto）
        { "userName": "xxx", "aiName": "Tsuki" }
      后端回
        { "code": 200, "message": "预人设成功",
          "data": { "reply": "AI的开场白",
                    "selected": { "tags": ["妹妹","温柔"],
                                  "avatarUrl": "Resource/Avatar/xxx.jpg" } } }
        失败: { "code": 400, "message": "用户不存在|缺少性别|昵称" } 或 "出错了:..."
      后端处理流程
        按 userName 取 gender/callName/apiKey → 从库拿全部 tags 和 avatars(id+description)
        → SwitchFormat.FormatDict 组 pyai 载荷 → POST 127.0.0.1:10086/api/pre
        → 拿回 {reply, selected:{tags, avatarId}}
        → 用 avatarId 反查 GetAvatarByIdAsync 得到 Url
        → 最终返回给前端的是 avatarUrl（相对路径），不是 avatarId
      注意 该接口【只算不存】，真的落库要等 #4

  #4  申请好友（落库）           POST /api/ApplyFriend/apply
      前端发（ApplyFriendDto）
        { "tags": ["妹妹"], "avatarUrl": "http://localhost:5108/Resource/Avatar/x.jpg",
          "preReply": "开场白", "userName": "真人的名字", "aiName": "Tsuki" }
      后端回
        { "code": 200, "message": "落库成功!", "data": { "sessionId": 13 } }
        失败: { "code": 400, "message": "根本没有这个用户" }
      后端处理流程（顺序敏感）
        AddAIAsync(aiName) → SaveTagAsync(tags, aiId) → SaveAvatarAsync(avatarUrl, aiId)
        → GetUserIdAsync(userName) → CreateSessionAsync(userId) → JoinSessionAsync(sessionId, aiId)
        → SaveChatInMessageAsync(sessionId, aiId, preReply)
      约定
        前端把预人设拿到的 reply/tags/avatarUrl 原样回传，这里才真正建好友关系
        返回的 sessionId 前端存进 localStorage["sessionId_<aiName>"] 并绑到好友对象

  #5  上传文件                    POST /api/...（未实现）
      前端 uploadFileAsync POST '' 空地址，接口还没写；UploadFile 类型也是空的

四、服务间内部协议（不经过浏览器，CS ↔ Python）
================================================================================
  统一约定：C# 用 record 定义，System.Text.Json 默认 camelCase 输出，所以 C# 的
  SessionDict 会序列化成 "sessionDict"；Python 侧按小写驼峰读取。

  #A  CS → pyai  常规聊天         POST http://127.0.0.1:10086/api/ai
      AiPayload 结构（cs/Dtos.cs）
        { "apiKey": "sk-xxx",
          "sessionId": 12,
          "messages": { "用户昵称": [ { "role": "user|assistant", "content": "..." } ] } }
      pyai 回（AIChatDto）
        { "aiName": "用户昵称", "sessionId": 12, "message": "回复文本", "type": "text" }
      对应代码 pyai: Controller/ordinary_chat.py + Core/parse.py:get_info_from_chat
        parse 读 apiKey / sessionId / messages，取 messages 的第一个 key 当名字
      pyai 内部
        读 prmp/prmp_chat.txt 当 system 提示词 → 拼 history → OpenAI(apiKey,
        base_url=https://api.deepseek.com, model="deepseek-v4-pro") → 返回 content

  #B  CS → pyai  预人设           POST http://127.0.0.1:10086/api/pre
      PrePersonPayload 结构（SwitchFormat.FormatDict 产出）
        { "apiKey": "sk-xxx",
          "sessionDict": {
            "真人的名字": {
              "aiName": "Tsuki",
              "session": [],
              "tags": ["妹妹", "温柔"],
              "avatars": [ { "id": 1, "description": "米黄色头发蓝瞳开心小萝莉..." } ],
              "gender": "boy",
              "callName": "olderBrother" } } }
      pyai 回（PrePersonReplyDto）
        { "reply": "开场白", "selected": { "tags": ["妹妹"], "avatarId": 1 } }
      对应代码 pyai: Controller/pre_person.py + Core/parse.py:get_info_pre
        parse 读 apiKey / sessionDict，取第一个 key 当 user_name
      pyai 内部
        to_promp_file_pre() 把 tags/avatars/名字/性别/称呼 渲染进 prmp/prmp_pre.txt
        → 发 "打个招呼吧~" → 要求模型返回 JSON {reply, selected:{tags,avatarId}}
        → parse_reply_to_dict 解析 → get_reply_selected 提取
        → 用 avatarId 在 avatars 里找 description → to_promp_file_normal() 生成
          prmp/prmp_chat.txt（把选中的人设固化成后续聊天的 system 提示词）

  #C  Python → DeepSeek
      model "deepseek-v4-pro"，stream=false，reasoning_effort="high"，
      extra_body={"thinking":{"type":"enabled"}}，base_url https://api.deepseek.com
      注意 每次请求都由函数内 new OpenAI(api_key=...) 构造客户端，key 来自前端

  #D  提示词文件（pyai/prmp/，运行时产物，每次请求被覆盖重写，同时又是下次的输入）
      prmp_pre.txt   预人设用：名字/用户名/性别/称呼 + 全部 tags + 全部 avatars
                     + 强制 JSON 输出格式要求
      prmp_chat.txt  常规聊天用：名字/头像描述/用户名/性别/称呼 + 已选 tags
                     + 「不要用圆括号包动作」等口吻约束；由预人设流程产出

六、已发现的前后端/服务间不一致（仅记录，未改代码）
================================================================================

  D1  CS ↔ pyai 预人设字段名对不上 【会导致预人设必然失败】
      CS 发送：{ "apiKey", "sessionDict": { ... } }   （PrePersonPayload.sessionDict）
      pyai 读取：prop_dict.get("sessionDict")
      → 若实际 JSON 键是 userNameDict / 或键名大小写不符，pyai 取到 None
        → list(None.keys())[0] 直接抛异常
      需要两侧对齐：外层字典键名必须一致（SwitchFormat.cs 注释里写的还是
      userNameDict，而 record 属性是 sessionDict，以实际序列化结果为准）

  D2  CS → pyai 预人设载荷缺 sessionId
      AiPayload 有 sessionId，PrePersonPayload 没有；pyai 侧也不读它
      目前不影响功能，但 pyai 注释里仍写着 "sessionId": 123，属于文档残留

  D3  聊天接口返回字段名不一致 【前端会拿不到回复】
      前端 ChatData 读的是 data.reply
      后端 chat1 返回的是 data.message（匿名对象 new { reply.sessionId, reply.message }）
      → 前端 replyMessage 为 undefined，界面上会显示 "出现错误，请稍后再试"
      （后端代码里已有 TODO：前端要求格式并非如此）

  D4  头像 URL 形态不一致 【会导致好友头像落库失败】
      pyai 返回 avatarId（数字）；CS 用它反查得到相对路径 "Resource/Avatar/x.jpg"
      前端 preAiPerson 拼成绝对地址 http://localhost:5108/Resource/Avatar/x.jpg
      并把这个绝对地址回传给 applyFriendAsync
      而 DbIO.SaveAvatarAsync 是 FirstOrDefault(x => x.Url == avatarUrl) 精确匹配
      库里的 Url 全是相对路径 → 匹配不到 → return NotFound，AI 的 AvatarUrlId 不会写入
      两种修法：前端回传相对路径，或后端匹配时先剥掉 baseUrl / 只比文件名

  D5  SaveTagAsync 的空列表分支逻辑反了 【标签可能永远不落库】
      代码：if (tagRepetition.Count == 0) return IOState.Found;
      含义：当「已经关联过的标签」一个都没有时就直接返回，不执行后面的批量插入
      → 首次给某个 AI 打标签时 add 列表永远为空
      正确逻辑应是把条件反过来（或者删掉这个提前 return）

  D6  注册接口返回的 id 类型
      CS 返回 saved.Id（int），前端 RegisterData 声明为 id?: string
      实际能跑（都当字符串拼进 localStorage），但类型标注与真实返回不符

  D7  预人设"只算不存"
      /api/PrePerson/preperson1 只返回 reply + selected，不写任何表；
      真正建好友/建会话/存消息在 /api/ApplyFriend/apply
      前端必须把 #3 的结果原样喂给 #4，中间丢了就白算

  D8  登录接口在后端不存在
      WPF 端 Login_VM 里有 昵称+密码 的登录表单，DTO-Format.json 也登记了
      { userName, userPassword }，但 CS 只有 /api/Auth/register，没有 login
      目前实际靠「注册即发 token + localStorage 免登录守卫」顶替登录

  D9  WPF 与 Electron 是两套并行前端
      Wpf-end 只有登录/注册 2 个页面，校验规则是本地写的（昵称字母汉字、
      密码含字母数字特殊字符等），没发任何 HTTP；真正在用的是 Face/bot-face

  D10 pyai 的模型名 "deepseek-v4-pro" 大概率无效
      DeepSeek 官方模型名为 deepseek-chat / deepseek-reasoner
      该调用预计直接报错（模型不存在）
